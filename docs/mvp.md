# Задача 1: разбор похожих приложений

Статус: ✅ research собран 2026-08-28. Решения по блокам 1–5 — за Sergey (ниже помечены ⬜).

Разобраны: Paprika 3, AnyList, Plan to Eat, Mealime, Samsung Food (ex-Whisk), Bring!, Replay Recipes, ReciPath (offline-first на Supabase). Разрезы — ровно пункты списка задач выше.

## Блок 1. Когда регистрация

| Приложение | Гейт | Как устроено |
|---|---|---|
| Paprika 3 | нет | Платная покупка, работает полностью локально. Аккаунт (Paprika Cloud) — только ради синка между устройствами |
| AnyList | нет | Локальные списки сразу; аккаунт нужен только для синка и шаринга |
| ReciPath (offline-first, Supabase) | нет | Прямая цитата подхода: «всё локально, аккаунты опциональны, только для синка» |
| Mealime | мягкий | Быстрый free-аккаунт на входе, но онбординг короткий |
| Plan to Eat | жёсткий | Аккаунт обязателен, инвайты по username → у всех участников он уже есть |
| Samsung Food | жёсткий | Аккаунт обязателен, шаринг тоже завязан на аккаунт |

Вывод: доминирует «локально сразу, аккаунт когда понадобится синк/шаринг». Жёсткий гейт держат те, у кого шаринг — ядро продукта.

**У нас сейчас жёсткий гейт:** без сессии рендерится только `sign-in` (`Stack.Protected` в [_layout.tsx](../src/app/_layout.tsx)), плюс PowerSync без JWT вообще не стартует.

Варианты:

| # | Вариант | Плюсы | Минусы |
|---|---|---|---|
| A | Оставить жёсткий гейт | 0 работы | Отвал на первом экране, юзер платит регистрацией до того, как увидел ценность |
| B | **Supabase Anonymous Sign-In** при первом запуске | Приложение работает сразу и офлайн; PowerSync получает валидный JWT; при линковке email `user id` **не меняется** → данные переезжают без миграции; `owner_id = auth.uid()` продолжает работать | Включить Anonymous + Manual Linking в дашборде (Sergey); мусорные юзеры/боты → нужна капча или лимит; RLS желательно разделить по claim `is_anonymous` |
| C | Локальный SQLite без auth, PowerSync только после регистрации | «Честно локально» | Два режима хранения и два пути записи → двойной код, перенос данных при регистрации руками. Не рекомендую |

**Рекомендация: B.** Единственный вариант, где не ломается текущая архитектура: анонимная сессия — обычная сессия, весь стек (коннектор, стримы, RLS, сторы) остаётся как есть. Линковка — `supabase.auth.updateUser({ email })` при включённом manual linking.

Что придётся доделать при B: экран «Войти/создать аккаунт» переезжает из гейта в настройки + мягкие подсказки в точках, где аккаунт реально нужен (шаринг, второе устройство). Конфликт «анонимные данные vs данные существующего аккаунта» при входе в **уже существующий** аккаунт — решаем как «оставляем данные аккаунта, анонимные предлагаем перенести» либо просто предупреждением (Supabase этот конфликт не решает, это наш код).

✅ **Решение Sergey (2026-08-28): вариант A — жёсткий гейт остаётся.**

Причина: анонимных юзеров нет → не нужны капча и защита от ботов, не нужен manual linking, нет конфликта «анонимные данные vs существующий аккаунт» при входе, нет миграции данных. Плюс `owner_id` всегда реальный юзер — шаринг (блок 2) не упирается в «как пригласить анонима».

Кода не требуется: `Stack.Protected` в [_layout.tsx](../src/app/_layout.tsx) уже реализует это.

Принятая цена: отвал на первом экране. Смягчение — позже и дёшево (продающий sign-in, соцвходы вместо пароля), в MVP не делаем.

## Блок 2. Шаринг

| Приложение | Что шарится | Кого приглашают | Механика |
|---|---|---|---|
| Paprika 3 | всё | — | Официальный ответ саппорта: делить один аккаунт на всех. Шаринга нет вообще |
| AnyList | весь набор рецептов + план питания целиком | по email | Recipes → Actions → Share Recipes & Meal Plan |
| Plan to Eat | план + список | по username | Обе стороны обязаны иметь аккаунт |
| Samsung Food | список / план | по email **или по ссылке** | «Anyone with the link can view and edit». Присоединение к общему плану **заменяет** личный план |
| Bring! | список | по ссылке | Список — самостоятельная сущность с участниками |

Вывод: рынок почти везде — **household-модель** («шарим всё с семьёй»), а не per-record. Точечный шар одного рецепта существует, но как «отправить другу», а не как совместная работа.

**У нас схема мощнее рынка:** `shares(resource_type, resource_id, user_id, role)` для `week | recipe | grocery_list`, стримы уже с транзитивностью (шаришь неделю → уезжают и рецепты её слотов). Т.е. per-resource уже работает на бэке — вопрос только в UI и в том, что показывать юзеру.

| # | Вариант | Плюсы | Минусы |
|---|---|---|---|
| A | Household: одна кнопка «пригласить в семью», шарится всё | Понятнее всего, совпадает с рынком, минимум UI | Нужен `resource_type = 'all'` или space-модель (в [sync-plan.md](sync-plan.md) заложено как расширение); нельзя «показать только один рецепт» |
| B | Per-resource: «поделиться этой неделей / рецептом» | Схема и стримы уже готовы, менять нечего; гибко | Больше экранов, юзеру надо объяснять модель; типичный сценарий «жена видит всё» превращается в N приглашений |
| C | **Гибрид:** household по умолчанию + «отправить рецепт» точечно | Покрывает и семью, и «скинуть рецепт другу» | Две механики в UI |

Механика приглашения (в sync-plan это пункт 1.3, до сих пор ⬜):

| Способ | Плюсы | Минусы |
|---|---|---|
| По email | Мгновенно, как AnyList | Из клиента искать юзера по email нельзя (RLS/приватность) → нужна Edge Function; не работает для незарегистрированных; утечка факта «такой юзер есть» |
| **По ссылке-токену** | Работает для ещё не зарегистрированных (перешёл → регистрация → сразу в семье); deep link уже возможен — `expo-linking` в зависимостях | Нужна таблица `invites` (токен, срок, роль, одноразовость) отдельной миграцией |

**Рекомендация: C + приглашение по ссылке.** Email-поиск не делать — он тянет Edge Function и не решает главный кейс (пригласить того, кого в приложении ещё нет).

✅ **Решение Sergey (2026-08-28): вариант C — семья + точечный шаринг рецепта. Приглашение — только по ссылке-токену. Шаринг рецепта = копия, не доступ.**

**Семья.** Создаётся явно (можно жить без неё). Владелец жмёт «Создать семью» → генерит ссылку-инвайт. Приглашённый открывает ссылку → **сначала регистрация/вход** (гейт из блока 1) → токен применяется после входа → он в семье. Участники семьи видят весь датасет владельца: недели, рецепты, grocery-списки.

**Токен переживает регистрацию:** сохраняем его при открытии ссылки, применяем после успешного входа.

**Шаринг рецепта — копия.** Получатель клонирует рецепт себе, дальше рецепт его: правки владельца не долетают, отозвать нельзя, строка в `shares` не создаётся. Получателю всё равно нужен аккаунт (гейт A). Публичная веб-страница рецепта для незарегистрированных — не в MVP.

**Фото при копировании не дублируется:** копия ссылается на тот же объект в Storage, дедуп по хэшу содержимого (см. блок 3).

Email-инвайт отклонён: тянет Edge Function, не решает главный кейс (пригласить того, кого в приложении ещё нет), палит факт существования юзера.

Что делать в коде (детализация — при реализации): таблицы `families` / `family_members` / `invites`, `resource_type = 'family'` либо переход на space-модель, правка sync-streams под семью, deep link на `expo-linking`, экран «Семья» в настройках, действие «Поделиться рецептом» → ссылка → импорт копии.

## Блок 3. Фото

Сейчас: в схеме `recipes.photos jsonb` = массив URL, кода загрузки нет — картинки нигде не хранятся.

Ключевой факт по твоему вопросу из списка задач: **«хранить локально» и «шарить» несовместимы напрямую.** Если файл только на устройстве — у второго юзера его нет. Индустриальный ответ один: метаданные в БД, файлы в объектном хранилище, локальный кэш на устройстве.

У PowerSync это штатный сценарий — attachment queue: фото пишется на диск локально, строка-метаданные едет обычным синком, очередь заливает файл в Supabase Storage с ретраями, на втором устройстве watch видит id → скачивает. Офлайн не ломается. Пакет `@powersync/attachments` **deprecated** — функциональность встроена в SDK; локальный адаптер хранения — `@powersync/attachments-storage-react-native`.

| # | Вариант | Итог |
|---|---|---|
| A | **PowerSync attachments + Supabase Storage** | Рекомендую. Офлайн-first сохраняется, шаринг работает, ретраи из коробки |
| B | Только локально (`expo-file-system`) | Шаринг фото невозможен, второе устройство пустое. Противоречит mvp |
| C | Прямой upload в Storage при сохранении рецепта | Ломает офлайн: без сети сохранение либо блокируется, либо фото теряется |

Цена варианта A: bucket + RLS-политики под те же правила, что `shares` (Sergey в дашборде); ресайз/сжатие перед заливкой (Free-план Supabase Storage — 1 GB); чистка файлов при tombstone рецепта.

✅ **Решение Sergey (2026-08-28): вариант A — PowerSync attachments + Supabase Storage.**

Отдельное требование Sergey: рецептов много → фото много, база и хранилище не должны заплывать. Дисциплина хранения (принята вместе с вариантом A):

- **Сжатие перед заливкой** — `expo-image-manipulator`, ~1600 px по длинной стороне, jpeg q≈0.7: 200–400 КБ вместо 3–5 МБ с камеры. Оригинал не храним.
- **Отдельная превьюшка** для списков/коллажей (~300 px), чтобы лента не тянула полноразмерные файлы.
- **Лимит фото на рецепт** — конкретное число ⬜ за Sergey (предложение: 5).
- **Дедуп по хэшу содержимого** — копия рецепта (блок 2) ссылается на тот же объект, файл в Storage не дублируется.
- **Удаление файлов при tombstone рецепта** — иначе Storage растёт вечно, tombstone-строки его не чистят.
- **LRU-чистка локального кэша** — на устройстве держим не весь архив.

Инфраструктура за Sergey: bucket + RLS-политики под те же правила, что `shares`/семья. Free-план Supabase Storage — 1 GB.

## Блок 4. Магазины и цены

**Всё упирается в рынок — это блокирующий вопрос.**

**US/Canada — задача решена готовым API.** Instacart Developer Platform: эндпоинты «Create recipe page» и «Create shopping list page» — отдаём список ингредиентов, получаем ссылку; юзер открывает, выбирает магазин, товары уже подобраны в корзину, дальше правит сам. Это буквально твой сценарий «собрать корзину, дальше пользователь редактирует». Матчинг «строка ингредиента → конкретный товар» и цены — на их стороне. Есть и MCP-интеграция (`create-recipe`, `create-shopping-list`) для агентов.

**Россия — готового пути нет.** Публичных API у Купер / Яндекс Лавка / Самокат / ВкусВилл нет. Что реально доступно:

| Путь | Оценка |
|---|---|
| Партнёрская/affiliate программа сети | Единственный «белый» путь к корзине. Это переговоры, а не код. Для MVP недоступно |
| Парсинг витрин | Ломается при каждом релизе, юридически серо, антибот. Не рекомендую |
| Сервисы мониторинга цен (MarketParser, ParserData) | Платные, покрытие — маркетплейсы (WB/Ozon), продуктовые сети слабо |
| Чеки ОФД/ФНС | Цены постфактум и разрозненные, не витрина магазина. Не годится для «покажем лучшую цену сейчас» |

Вывод по пункту «по дефолту подсказка лучшей цены»: **в RU честно не реализуемо в MVP.** Обещать в UI цену, которой у нас нет источника, — хуже, чем не обещать.

Предложение сузить MVP до того, что даёт ценность без данных о ценах:

1. **Нормализация ингредиентов** — «200 г куриной грудки» → канонический продукт + количество + единица + отдел магазина. Здесь твоя мысль про дешёвые модели верна: дешёвая LLM, вызов **один раз на уникальную строку ингредиента**, результат кэшируется по хэшу → дальше бесплатно. Это же чинит существующую боль — сейчас `grocery_items` склеиваются по сырой строке.
2. Группировка списка по отделам магазина (овощи/молочка/бакалея) — самый заметный выигрыш в реальном походе в магазин.
3. Экспорт списка: шаринг текстом / deep link в приложение магазина без корзины.
4. Корзина и цены — отдельный этап после выбора рынка/партнёра.

## Блок 5. Режим готовки (фото + чекбоксы)

| Приложение | Что делают |
|---|---|
| Paprika 3 | Опция keep-screen-on, чекбоксы по ингредиентам и шагам |
| Plan to Eat | Отдельный Cooking View, экран не гаснет |
| Mealime / Yummly | Cook mode, экран не гаснет |
| Replay Recipes | Чекбоксы + тёмная тема + экран не гаснет |

Стандарт жанра: отдельный полноэкранный режим + экран не гаснет + чекбоксы, которые **не сохраняются как данные** (это состояние одной готовки, а не свойство рецепта).

**Рекомендация:** самый дешёвый блок из всех. `expo-keep-awake` (уже идёт с Expo), чекбоксы — локальный React-стейт. В БД и в синк не тащить: иначе чужой чекбокс будет прилетать тебе в середине готовки.

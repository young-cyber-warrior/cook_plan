# План: семья, шаринг рецептов копией, фото

## Краткая сводка

**Что делаем:** реализуем решения из [mvp.md](mvp.md) — блок 2 (шаринг) и блок 3 (фото). Блок 1 (регистрация) закрыт без кода, блоки 4–5 отложены.

**Три цели:**

1. **Семья.** Юзер явно создаёт «семью», зовёт по ссылке — участники видят весь его датасет: недели, рецепты, grocery-списки. Живой шаринг, правки видны в рантайме.
2. **Рецепт копией.** Любой рецепт можно отдать кому угодно ссылкой. Получатель забирает **копию**: рецепт становится его, связи с оригиналом нет.
3. **Фото.** Фото рецептов реально работают: снимаются офлайн, доезжают в облако, видны всем, кому рецепт доступен, и не раздувают хранилище.

**На чём стоим:** уже есть Supabase + PowerSync + MobX (см. [sync-plan.md](sync-plan.md)). Ничего из этого не переделываем — только достраиваем.

### Ключевые решения (приняты до написания плана, менять — только осознанно)

**Семья не добавляет колонку в таблицы данных.** Доступ считается через владельца: «я вижу запись, если её `owner_id` — я сам ИЛИ он в моей семье». Альтернатива (`family_id` в каждую из 8 таблиц) отвергнута: миграция всех таблиц, бэкфилл, правка каждого INSERT в сторах, и главное — при вступлении в семью пришлось бы «переносить» старые записи. Текущий вариант даёт это бесплатно: вступил — все твои прошлые данные видны семье, вышел — перестали.

Плата: нельзя спрятать от семьи отдельную запись. Это ровно то, что решено в mvp (вариант C — «семья видит всё»).

**Одна семья на юзера.** Уникальный индекс по `user_id` в `family_members`. Множественные семьи ломают модель «вижу всё, что видит семья» и усложняют UI без сценария.

**Приглашение принимается через SECURITY DEFINER функцию.** Приглашённый до вступления не может прочитать строку `invites` (RLS её закрывает), поэтому `accept_invite(token)` выполняется с правами владельца функции: сама проверяет токен и вставляет участника. Обычным INSERT из клиента это не сделать.

**Токен инвайта — 32 случайных байта, `expo-crypto`.** Не UUID: UUID v4 угадать нельзя, но токен ещё и живёт в ссылке — берём явную криптографическую случайность.

**Фото переезжают из `recipes.photos jsonb` в таблицу `recipe_photos`.** Причины: (1) построчный LWW — два человека добавляют по фото офлайн, оба выживают, а jsonb-массив затирается целиком; (2) на каждое фото нужен свой `id`, он же id вложения в PowerSync; (3) дедуп и чистка по строкам, а не парсингом массива.

**Файлы — PowerSync attachments + Supabase Storage.** В SDK v2 очередь вложений встроена (пакет `@powersync/attachments` deprecated), локальный адаптер — `@powersync/attachments-storage-react-native`. Фото пишется локально сразу, очередь заливает при сети, у второго устройства скачивается по `id`. Офлайн не ломается.

**Дедуп по SHA-256 содержимого.** Путь в бакете — `recipes/<hash>.jpg`. Одинаковый файл (в первую очередь — копия рецепта) лежит в Storage один раз.

Файл: [20260828120000_family_access.sql](../supabase/migrations/20260828120000_family_access.sql). Отклонения от текста плана:

- Хелперы — не просто `stable`, а **`security definer`**. Иначе `my_family_id()` читает `family_members` под RLS, а политика `family_members` сама зовёт `my_family_id()` → бесконечная рекурсия.
- Добавлен четвёртый хелпер `my_family_role()` — без него не выразить «удалить участника может только владелец» (шаг 3.4), а инлайнить `exists` по `family_members` в её же политику нельзя по той же причине рекурсии.
- В политиках дочерних таблиц условие `child.owner_id = parent.owner_id` заменено на `can_write_owner(child.owner_id)`. Старое ломало семью: участник Б добавляет ингредиент в рецепт А, `owner_id` строки — Б, владелец рецепта — А, проверка не проходила. Доступ к детям всё равно считается через родителя, а стримы тянут их по `parent_id`.
- `families_select` дополнительно пускает `owner_id = auth.uid()`. Без этого создание семьи невозможно: на момент вставки своей строки в `family_members` у юзера ещё нет членства → `my_family_id()` null → только что созданная семья ему не видна → `exists`-проверка в `family_members_insert` падает.

**1.1 — таблицы.**

- `families` — `id`, `owner_id` (создатель), `name`, сквозные колонки как у остальных (`deleted`, `created_at`, `updated_at`, `field_times`, триггер `lww_touch`).
- `family_members` — `id`, `family_id`, `user_id`, `role` (`owner` | `member`), сквозные колонки. Уникальный индекс по `user_id` среди неудалённых — одна семья на юзера. Создатель семьи вставляет себе строку `owner` тем же действием.

**1.2 — хелперы.** Три `stable` SQL-функции, чтобы правило доступа жило в одном месте (иначе один и тот же `exists (...)` расползётся по ~24 политикам):

- `my_family_id()` → `family_id` текущего юзера или `null`.
- `can_read_owner(p_owner uuid)` → `p_owner = auth.uid()` ИЛИ `p_owner` состоит в `my_family_id()`.
- `can_write_owner(p_owner uuid)` → сейчас то же самое: внутри семьи все равны, ролей «только чтение» не вводим. Отдельная функция нужна, чтобы позже добавить viewer-роль, не переписывая политики второй раз.

**1.3 — RLS.** В существующих политиках ([20260810120000_init_sync_schema.sql](../supabase/migrations/20260810120000_init_sync_schema.sql)) условие `owner_id = auth.uid()` заменяется на `can_read_owner(owner_id)` / `can_write_owner(owner_id)`. Дочерние таблицы (`recipe_ingredients`, `meals`, `grocery_items`) проверяют доступ через родителя — там меняется вложенная проверка родителя. Ветки `is_shared_with_me(...)` остаются нетронутыми (см. «Подводные камни»).

Отдельно `categories`: сейчас политика строго `owner_id = auth.uid()`, при этом чужая категория обязана быть видна ради шаренного рецепта — добавляем ветку `can_read_owner` и ветку «категория используется доступным мне рецептом».

Файл: [20260828130000_invites.sql](../supabase/migrations/20260828130000_invites.sql). Отклонения от текста плана: колонки `created_by` нет — создатель это `owner_id` из сквозных колонок, две колонки с одним значением не нужны. `accept_invite` возвращает `jsonb` вида `{ok, reason}` / `{ok, family_id}`; коды отказа: `unauthenticated`, `not_found`, `revoked`, `expired`, `exhausted`, `already_in_family`.

**2.1 — `invites`:** `id`, `family_id`, `token` (уникальный), `created_by`, `expires_at` (по умолчанию +7 дней), `max_uses` (по умолчанию `null` = без лимита), `uses` (счётчик), `revoked`, сквозные колонки. Читать строку может только семья-владелец — приглашённый до вступления не читает ничего.

**2.2 — `accept_invite(p_token text)`.** SECURITY DEFINER, `search_path = ''`. Логика по шагам: найти инвайт по токену → проверить `not revoked`, `not deleted`, `expires_at > now()`, `max_uses` не исчерпан → проверить, что юзер ещё не в семье (иначе вернуть понятную ошибку — «сначала выйди из текущей семьи») → вставить `family_members(family_id, auth.uid(), 'member')` → увеличить `uses` → вернуть `family_id`. Возврат — структурированный результат (успех/причина отказа), чтобы UI показал текст, а не «RLS violation».

**2.4 — ссылка.** Формат `myapp://invite/<token>` (схема приложения — в `app.json`). Флоу с гейтом варианта A:

1. Юзер Б открывает ссылку.
2. Приложение сохраняет токен в AsyncStorage как `pendingInvite` — **до** проверки сессии.
3. Нет сессии → обычный экран регистрации/входа (гейт).
4. После успешного входа `RootStore` видит `pendingInvite` → `supabase.rpc('accept_invite')` → чистит ключ.
5. Успех → PowerSync подтягивает датасет семьи; отказ → баннер с причиной.

Токен обязан переживать регистрацию — иначе приглашённый после входа окажется один, без объяснений.

Универсальные ссылки (https, открываются без установленного приложения) — не в этом этапе: требуют домена и файлов ассоциации. Кастомной схемы для MVP достаточно.

Отклонения от текста плана:

- **Бакет создаётся миграцией**, а не руками в дашборде: `insert into storage.buckets` с `public = false`, `file_size_limit = 5 МБ`, `allowed_mime_types = {image/jpeg}`. Воспроизводимо и не требует ручного шага.
- **Политика `insert` на бакет — не «только свои пути».** Путь считается от хэша содержимого (`recipes/<hash>.jpg`), он одинаков у оригинала и копии, привязать его к юзеру нельзя. Проверяется префикс `recipes/`, тип и размер ограничены настройками самого бакета.
- **Лимит фото — триггер, а не `check`.** `check` не умеет считать соседние строки; `enforce_recipe_photo_limit` перед insert/update кидает `23514` (коннектор считает этот код фатальным и не зациклится на ретраях).
- **Отдельного превью ~300 px нет.** В схеме `recipe_photos` из плана нет колонки под второй файл, а заводить вторую строку-вложение на каждое фото — двойной трафик и лишняя сущность. Коллаж и просмотрщик берут тот же локальный файл: он уже ужат до 1600 px и читается с диска, сети в этом месте нет.
- **Имя файла вложения — `<row_id>.jpg`, путь в бакете — из `metaData`.** `saveFile` не принимает произвольное имя, поэтому хэш кладётся в `metaData` вложения, а remote-адаптер собирает из него `recipes/<hash>.jpg`. Дедуп в Storage сохраняется: одинаковое содержимое → один объект (`upsert: true`).

**4.1 — бакет.** Private (не public): публичный бакет = любой в интернете читает файл по URL, RLS не спасёт. Политики на `storage.objects`:

- `select` — разрешён, если путь упомянут в неудалённой строке `recipe_photos`, читаемой мной (те же хелперы `can_read_owner`, что в этапе 1). Т.е. доступ к файлу следует за доступом к рецепту.
- `insert` — только в свои пути, с ограничением по типу и размеру.
- `delete` — только владельцу строки (см. 4.7).

**4.2 — `recipe_photos`:** `id`, `recipe_id`, `owner_id`, `storage_path`, `content_hash`, `width`, `height`, `bytes`, `position`, сквозные колонки. Колонка `recipes.photos` удаляется, вместе с ней — `photos` из клиентской схемы, из списка jsonb-полей коннектора ([connector.ts:24](../src/sync/connector.ts#L24)), из маппера и из INSERT в `recipes-store`. Реальных данных в ней нет — это черновик MVP, миграция данных не нужна.

**4.3 — пакеты.** Очередь вложений встроена в `@powersync/react-native@2.x`, отдельный пакет `@powersync/attachments` **deprecated** — ставим только локальный адаптер `@powersync/attachments-storage-react-native` (+ `expo-file-system`, обязателен на Expo 54+). Нативные модули → dev client пересобирается.

**4.4 — очередь.** `AttachmentTable()` добавляется в `AppSchema` (таблица локальная, на сервер не едет — синкается наша `recipe_photos`). `AttachmentQueue` получает: `localStorage` = `ExpoFileSystemStorageAdapter`, `watchAttachments` = watch по `recipe_photos` (id вложения = id строки), `remoteStorage` = адаптер с тремя методами на `supabase.storage.from('recipe-photos')` — `upload` / `download` / `remove`. Подписанные URL не нужны: `supabase-js` уже ходит с JWT юзера, политики бакета применяются.

Запуск/останов очереди — в `RootStore`, рядом с `connect`/`disconnectAndClear`, по тому же жизненному циклу сессии.

**4.5 — пайплайн добавления.** Порядок важен:

1. Выбор из галереи или съёмка (`expo-image-picker`).
2. **Сжатие сразу** — `expo-image-manipulator`, ~1600 px по длинной стороне, jpeg q≈0.7. Оригинал не сохраняем нигде: 3–5 МБ с камеры превращаются в 200–400 КБ.
3. Превью ~300 px — отдельным файлом, для коллажей и списков, чтобы лента не тянула полноразмер.
4. SHA-256 сжатого файла (`expo-crypto`) → `content_hash`, путь `recipes/<hash>.jpg`.
5. Если строка с таким `content_hash` уже видна — файл не заливаем повторно, создаём только строку `recipe_photos` на тот же путь.
6. Иначе — строка + постановка вложения в очередь.

Лимит фото на рецепт — **3**. Проверяется в UI и на сервере.

**4.6 — UI.** Существующие [recipe-collage.tsx](../src/features/day-card/components/recipe-collage.tsx) и [photo-viewer.tsx](../src/features/day-card/components/photo-viewer.tsx) уже принимают `string[]` — они не переписываются, меняется только источник: вместо URL из jsonb приходят локальные `file://` пути из очереди вложений. Пока файл не скачался — плейсхолдер. В редакторе рецепта — добавление, удаление, порядок.

**4.7 — уборка.** Два разных механизма, не путать:

- **Локальный кэш** — очередь сама архивирует давно не используемые файлы (`archivedCacheLimit`), весь архив фото на устройстве не лежит.
- **Файлы в Storage.** При tombstone рецепта его строки `recipe_photos` тоже тумбстонятся, но файл удалять вслепую **нельзя** — из-за дедупа на него может ссылаться копия рецепта у другого юзера. Порядок: RPC `photo_refcount(hash)` (SECURITY DEFINER, считает все живые ссылки, в том числе чужие) → если 0, клиент-владелец вызывает `storage.remove`. Гонка (кто-то копирует рецепт ровно в этот момент) теоретически возможна — цена ошибки: потерянная картинка у копии, не потеря данных. Полноценный сборщик мусора по расписанию — эскалация, не MVP.

## Этап 5. Шаринг рецепта копией

| # | Шаг | Ответственный | Статус |
|---|-----|---------------|--------|
| 5.1 | Миграция: `recipe_snapshots` + `import_shared_recipe(p_token)` | **Claude** → применяет **Sergey** | ✅ / ⬜ применить |
| 5.2 | Действие «Поделиться рецептом» → снапшот → ссылка | **Claude** | ✅ |
| 5.3 | Роут `recipe/[token]`: превью и кнопка «Добавить себе» | **Claude** | ✅ |

Файлы: [20260828150000_recipe_snapshots.sql](../supabase/migrations/20260828150000_recipe_snapshots.sql), [share.ts](../src/features/recipes/lib/share.ts), [recipe/[token].tsx](../src/app/recipe/[token].tsx).

Отклонения от текста плана:

- **Добавлена вторая RPC — `preview_shared_recipe(p_token)`.** Получатель не имеет прав на чужой снапшот, значит превью из 5.3 он тоже прочитать не может. Обе функции `security definer`, обе доступны только `authenticated`.
- **В превью нет фото.** Политика чтения бакета привязана к строке `recipe_photos`, а у получателя её ещё нет — она появляется только при импорте. Показываются название, описание и ингредиенты; фото подтягиваются после «Добавить себе».
- **`recipe_snapshots` нет ни в клиентской схеме, ни в стримах.** Строка пишется напрямую через `supabase.from(...).insert` — поделиться без сети всё равно нельзя, а гонять снапшот через локальный SQLite и очередь CRUD незачем.
- **Срок жизни снапшота — 30 дней** (предложение плана), это `default` колонки `expires_at`.
- Генератор токена вынесен в [lib/token.ts](../src/lib/token.ts) — один на инвайты и на шаринг рецепта.

**5.1 — почему снапшот, а не payload в ссылке.** Затолкать рецепт в саму ссылку не выйдет: фото туда не влезут, а длина URL ограничена. Поэтому на «поделиться» создаётся строка `recipe_snapshots`: `id`, `token`, `owner_id`, `payload jsonb` (рецепт + ингредиенты + пути и хэши фото + подпись категории), `expires_at`, сквозные колонки. Снапшот **замороженный** — правки оригинала после шаринга в него не попадают, это и есть смысл «копии».

`import_shared_recipe(p_token)` — SECURITY DEFINER, тот же приём, что и с инвайтом (получатель не имеет прав на чужой снапшот): валидирует токен → находит или создаёт у получателя категорию по слагу → вставляет рецепт, ингредиенты и строки `recipe_photos` с **теми же** `storage_path`/`content_hash` → возвращает новый `recipe_id`.

Файлы фото при импорте не копируются — новые строки указывают на те же объекты (дедуп из 4.5). Именно поэтому политика чтения бакета в 4.1 привязана к `recipe_photos`, а не к владельцу рецепта: получатель копии обязан прочитать файл, который заливал не он.

**5.2/5.3 — UI.** В действиях рецепта — «Поделиться»: создаётся снапшот, ссылка `myapp://recipe/<token>` уходит в системный шит. У получателя ссылка открывает превью (название, фото, ингредиенты) с кнопкой «Добавить себе». Без сессии — тот же отложенный токен, что в 2.4.

## Подводные камни

- **Две механики доступа одновременно.** После этапа 1 в RLS и стримах живут и `shares` (per-resource, из sync-plan), и семья. UI у `shares` так и не появится — по mvp рецепт шарится копией. Чистка (снос `shares` из политик, стримов и клиентской схемы) — отдельный необязательный шаг, делать **после** того, как семья заработает и будет проверена; заранее не трогаем работающее.
- **CTE в sync streams не ссылается на CTE.** Список юзеров семьи придётся продублировать инлайном в каждом `accessible_*`. При любой правке — синхронно во всех ветках, иначе получатель увидит рассинхрон (неделя есть, рецептов нет).
- **Выход из семьи — потеря чужих данных на устройстве.** Записи выпадают из стрима и удаляются из локального SQLite. Это правильно, но в UI обязано быть предупреждение; выйти случайно нельзя.
- **`disconnectAndClear` при выходе из аккаунта** (описан в sync-plan) теперь опаснее: незалитые **фото** тоже в очереди. ⬜ Предупреждение при непустой очереди не сделано: `RootStore.stopAttachments` зовёт `stopSync` + `clearQueue` молча, незалитое фото пропадёт. Отдельный шаг, в нумерованных этапах его нет.
- **Публичный бакет — нет.** Только private + политики. Public-бакет отдаёт файл всем по прямому URL и обесценивает всю RLS.
- **Сжимать до постановки в очередь, а не после.** Иначе на диске и в Storage окажутся оригиналы с камеры и весь смысл дисциплины хранения теряется.
- **Free-план Supabase Storage — 1 ГБ.** При ~300 КБ на фото и лимите 5 фото на рецепт это тысячи рецептов, для MVP достаточно, но за расходом следить.
- **Deep link требует dev client** с прописанной схемой; в Expo Go проверить не выйдет.
- **Пикер категорий показывает только свои.** `toCategories` в [mappers.ts](../src/stores/mappers.ts) фильтрует по `owner_id === auth.userId`. Рецепты семьи придут вместе со своими категориями, но в выпадашке при создании рецепта чужих категорий не будет — то есть у каждого участника свой набор. Всплывёт на сценарии 6.1. Решать не стал: относится к UI рецептов, а не к семье, и требует решения «показывать чужие категории или мержить по слагу».
- **Участники в UI без имён.** `auth.users` наружу не отдаётся, в `family_members` только `user_id`. Экран показывает «Ты» и первые 8 символов id остальных. Нормальные имена — это либо публичная таблица `profiles`, либо RPC, отдающая почты своей семьи; в плане такого шага нет.
